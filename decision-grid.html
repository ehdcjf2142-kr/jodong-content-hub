조동 컨텐츠 허브 — 결정 비교표

미완성 프로젝트를 마무리하기 위해 고를 수 있는 선택지들입니다. 카드를 나란히 비교하고, 맨 아래에서 내 조합을 체크해 보세요.

쉬움 (비개발자 OK) 보통 (조금 도움 필요) 어려움 (개발 필요)
1

아카이브 검색 — 데이터를 어떻게 불러올까?

검색할 때 "목록"을 페이지에 실어 보낼지, 별도 파일(search-index.json)로 받을지 결정합니다.

A. 지금처럼 페이지에 실어서 추천 (콘텐츠 적을 때)

아카이브 페이지가 데이터를 한 번에 들고 와서 바로 검색합니다.

장점 구조가 단순하고, 지금 코드 그대로 쓸 수 있음
단점 글이·영상이 수백 개 넘으면 페이지가 무거워질 수 있음

이럴 때: 콘텐츠가 50개 미만이거나, 빨리 공개하고 싶을 때

B. JSON 파일로 따로 받기 보통

/search-index.json 파일을 내려받아 검색합니다. (이미 파일 생성 코드는 있음)

장점 콘텐츠가 많아져도 페이지가 가벼움
단점 검색 UI를 이 방식에 맞게 한 번 손봐야 함

이럴 때: 앞으로 100개 이상 쌓일 예정일 때

C. 당장은 A, 나중에 B 추천 (절충)

지금은 간단하게 가다가, 콘텐츠가 늘면 B로 옮깁니다.

장점 지금 할 일이 적고, 나중에 확장 가능
단점 나중에 검색 쪽을 한 번 더 수정해야 함

이럴 때: "일단 사이트부터 세상에 내보고 싶다" 할 때

2

검색 결과 — 어떤 순서로 보여줄까?

검색어와 "얼마나 비슷한지" 순 vs "최신 날짜" 순 중 무엇이 더 중요한지 정합니다.

A. 검색 잘 맞는 순 현재 방식

Fuse.js가 "비슷도 점수" 높은 것부터 보여 줍니다.

장점 키워드 찾기에 효율적
단점 "최신 글부터 보고 싶다"와는 다를 수 있음

이럴 때: "이 주제 관련 글 찾기"가 주 목적일 때

B. 최신 날짜순 추천

검색 결과를 날짜가 최근인 것부터 다시 정렬합니다.

장점 아카이브 느낌 — "요즘 뭐 올렸지?"에 맞음
단점 가장 관련 높은 글이 아래로 갈 수 있음

이럴 때: 통합 홈페이지에서 "최근 활동" 훑기가 중요할 때

C. 버튼으로 둘 다 보통

"정확도순 / 날짜순" 토글 버튼을 둡니다.

장점 방문자가 취향대로 고를 수 있음
단점 UI가 조금 더 복잡해짐

이럴 때: 검색 + 타임라인 둘 다 중요할 때

3

아카이브 — 검색만? 필터 버튼도?

플랫폼(유튜브·티스토리·네이버)이나 카테고리를 버튼으로 바로 고를 수 있게 할지 정합니다.

A. 검색만 가장 단순

지금처럼 검색창 + 전체 데이터 맵 테이블만 유지합니다.

장점 만들기·유지하기 제일 쉬움
단점 "유튜브만 보기" 같은 건 검색어로 해야 함

이럴 때: 콘텐츠가 아직 많지 않을 때

B. 최소 필터 2종 추천

플랫폼(YouTube / Tistory / Naver) + 유튜브 카테고리(3종) 버튼을 추가합니다.

장점 체감이 크고, 구현 난이도는 적당함
단점 태그별 세밀한 필터는 아직 없음

이럴 때: "한눈에 분류해서 보기"가 목표일 때

C. 필터 + 태그 칩 보통

플랫폼·카테고리 + 태그(예: #시, #로그라이크)를 칩으로 클릭해 좁힙니다.

장점 진짜 "내 도서관" 느낌
단점 UI·태그 관리가 더 필요함

이럴 때: 태그를 꾸준히 달 계획이고, 콘텐츠가 많을 때

4

"내 활동 전체" — 어디까지 넣을까?

지금은 유튜브 + 블로그 링크만 있습니다. 개인 아카이브를 어떤 형태로 넣을지 정합니다.

A. 링크 카드로 추가 추천 (쉬움)

새 JSON 파일에 제목·URL·날짜·태그만 넣어 카드로 보여 줍니다.

장점 지금 구조와 똑같아서 확장이 쉬움
단점 글 본문은 이 사이트에 안 보임 (외부 링크로 이동)

이럴 때: 노션·구글독·외부 자료 링크를 모으고 싶을 때

B. 글 본문도 이 사이트에 보통

마크다운(.md) 파일로 글을 쓰고, 사이트 안에 전용 페이지를 만듭니다.

장점 진짜 "내 홈페이지" — 글을 여기서 읽음
단점 글 쓰는 방식·관리가 늘어남

이럴 때: 블로그를 이 사이트로 옮기거나, 원문을 직접 호스팅하고 싶을 때

C. 지금 범위 고정, 나중에 확장 빠른 출시

유튜브 + 블로그 링크만으로 먼저 공개하고, 아카이브 확장은 다음 단계로 미룹니다.

장점 할 일이 적어서 빨리 세상에 낼 수 있음
단점 "전체 활동" 통합은 아직 덜 됨

이럴 때: 일단 MVP로 공개하고 피드백 받고 싶을 때

5

콘텐츠 업데이트 — 손으로? 자동으로?

유튜브 올리거나 블로그 쓸 때, 이 사이트 목록을 어떻게 갱신할지 정합니다.

A. 수동 (JSON 파일에 직접 추가) 추천 (시작)

새 영상·글마다 src/content/ 폴더에 JSON 파일을 하나 추가합니다.

장점 가장 안전하고, 깨질 일이 적음
단점 매번 손이 감 (에이전트/개발자 도움 받으면 쉬움)

이럴 때: 비개발자로 시작할 때, 월 몇 건 수준일 때

B. 반자동 (RSS·알림 → 복붙) 보통

유튜브·블로그 RSS나 알림으로 정보를 받아, JSON에 복사·붙여넣기만 합니다.

장점 제목·날짜·URL 입력이 줄어듦
단점 그래도 사람이 확인·정리는 해야 함

이럴 때: 업로드가 잦아지고, 수동이 부담될 때

C. 완전 자동 (API 연동) 어려움

YouTube Data API 등으로 채널·블로그를 자동 수집해 JSON을 생성합니다.

장점 거의 손 안 대도 최신 목록 유지
단점 API 키, 서버, 오류 처리 등 개발 필요

이럴 때: 콘텐츠가 매우 많고, 개발 지원이 있을 때

6

공개 전 — 꼭 손봐야 할 것들

기능 선택과 별개로, "진짜 사이트"로 쓰려면 아래 중 어디까지 할지도 정하면 좋습니다.

샘플 URL → 실제 링크로 교체 필수에 가까움

블로그 JSON에 example.tistory.com 같은 가짜 주소가 있습니다. 실제 글 URL로 바꿉니다.

파일: src/content/blog-links/*.json

도메인·SEO 설정 배포 시

astro.config.mjs의 site URL, robots.txt의 Sitemap 주소를 실제 Vercel/커스텀 도메인에 맞춥니다.

시점: Vercel에 첫 배포 후

GitHub + Vercel 배포 한 번만

저장소 푸시 → Vercel 연결 → npm run build 성공 확인. README에 체크리스트가 있습니다.

효과: 인터넷 주소로 누구나 접속 가능

콘텐츠 양 늘리기 지속

지금 샘플은 영상 6개 + 블로그 4개. 실제 채널·블로그 글을 JSON으로 더 넣으면 "통합 허브" 느낌이 살아납니다.

팁: 한 번에 다 안 넣어도 됨. 최근 10~20개부터
